# AGENTS.md

This file holds the repo's long-standing coding conventions — everyone (including AI agents) writing code in this repo must follow it. One-time technology choices live in [docs/tech-stack.md](./docs/tech-stack.md); this file only records conventions that stay in effect over time.

## Directory structure

- Organize entrypoints per WXT's convention: `entrypoints/popup/`, `entrypoints/sidepanel/`, `entrypoints/options/`, `entrypoints/background/`.
  - `popup`: opened by clicking the toolbar icon, a **read-only glance at the current site** — identifies the Worker, shows the active deployment's traffic split and versions, offers one-click version preview (override), and links out to the Cloudflare Dashboard. **Don't put heavy content here like stat numbers/Bindings/gradual-deployment controls, and no editing actions at all** — account/token info is read-only display, with no switcher (that's a low-frequency corrective action). Use two tests: never add anything that changes live traffic; for anything that needs an extra API request just to answer a question, weigh it carefully first — every additional request in the popup directly slows down the "click and glance" experience.
  - `sidepanel`: the full control panel, opened via the popup's button or Chrome's built-in entry point. **It does not auto-refresh when the browser tab changes** — it stays pinned to whichever tab it was opened against, and a tab change only surfaces as a banner at the top that the user has to click to switch (see `entrypoints/sidepanel/use-pinned-hostname.ts`). Before adding a new heavy data request, consider whether it should go through this "manual switch" mechanism instead of auto-refetching on every tab change. It owns the heavy operations — account switching, gradual-deployment control, bindings, etc. — and lays the page out "actions first, reference second": the highest-frequency Versions card comes first, and editing controls (like "Manage deployment") default to collapsed, only expanding when the user actively opens them. Don't show large editing forms expanded by default.
- Inside an entrypoint, organize by feature folder, not by type (no `components/`/`hooks/` grab-bags).
- **Hooks/components used by both popup and sidepanel with identical interaction behavior go in `shared/worker-panel/`** (e.g. `use-worker-lookup.ts`, `version-row.tsx`, `identity-header.tsx`) — don't duplicate one copy per entrypoint. **When both sides show the same data but support different interactions** (e.g. account info is read-only in popup but switchable/manageable in sidepanel), split it into two small components each owned by its own entrypoint (e.g. `entrypoints/sidepanel/account/account-control.tsx` + `entrypoints/popup/account-badge.tsx`) rather than cramming both into one component toggled by a prop. Only things used by a single entrypoint stay in that entrypoint's own feature folder.
- **`shared/ui/`**: pure UI primitives generated by shadcn/ui (`Button`, `Card`, `Dialog`, etc.), carrying no product/business knowledge, managed via `pnpm dlx shadcn@latest add <name>`; don't hand-edit these files' core structure before upgrading the shadcn version, though small style/variant tweaks are fine to make directly. By contrast, `shared/worker-panel/` holds business components that do carry product knowledge (e.g. `version-row.tsx`).
- Non-UI logic shared across multiple features goes in top-level `shared/` (e.g. `shared/cloudflare-api/`, `shared/storage/`).

## Naming conventions

- **Component file names**: kebab-case, e.g. `version-switcher.tsx`, `api-token-form.tsx`.
- **In-code component identifiers**: PascalCase, e.g. `export function VersionSwitcher() {}` — doesn't need to match the filename character-for-character, but must map one-to-one (`version-switcher.tsx` → `VersionSwitcher`).
- **Hook files**: `use-xxx.ts` (kebab-case), exported hook name in camelCase, e.g. `use-current-worker.ts` → `useCurrentWorker`.
- **Utility function files**: `xxx-utils.ts` (kebab-case), exported functions in camelCase.
- **Directory names**: kebab-case throughout.
- **Types/interfaces**: PascalCase, defined inline in whichever file uses them most; types shared across files go in a `types.ts` under the relevant feature or shared directory.

## Types and data validation

- TypeScript everywhere in the project; `any` is banned. When a type can't be determined, use `unknown` and narrow it.
- Every Cloudflare API response must be runtime-validated with a zod schema — never assume an external JSON payload actually matches the SDK's type declarations.

## Component patterns

- Function components + hooks only, no class components.
- Keep container components (which fetch and manage state) separate from presentational components (which only render from props) — avoid one component that both fetches and renders.
- Data-fetching logic belongs in the relevant feature's hook, not written as a bare `useEffect` + fetch directly in a component body.

## Error handling

- A failed Cloudflare API call must go through the shared error-display component/scheme (an error-code → user-readable-message map) — don't write a separate try/catch + local error state in every component.
- Network-layer error classification (auth failure / insufficient permission / rate limited / unknown error) is handled centrally in `shared/cloudflare-api/`; upper-layer components only ever consume the already-classified result.

## Auth and sensitive data

- API tokens are only ever stored in `chrome.storage.local`, never `chrome.storage.sync` (to avoid syncing them to a Google account in the cloud).
- No logging (`console.log`, error reporting, etc.) may print a token's plaintext value or any other sensitive field.
- Production builds strip debug `console.log` calls (keep `console.error`/`console.warn`).

## Least-privilege permissions

- Every new `permissions` or `host_permissions` entry added to `wxt.config.ts`/the manifest must be justified in its PR description — no "just in case" requests.

## Internationalization

- All user-facing copy goes through `chrome.i18n` (`_locales/<lang>/messages.json`) — never hardcode Chinese or English strings directly in components.
- When adding new copy, keep at least the `en` and `zh_CN` locale files in sync.

## Commit conventions

- Use Conventional Commits: `feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`, etc.
- One concern per commit — don't mix feature development with formatting/refactoring in the same commit.

## Testing

- Pure logic (hooks, utility functions, Cloudflare API wrappers) gets Vitest unit tests.
- Cross-entrypoint interactions (e.g. the side panel triggering a background header injection and verifying it took effect) get Playwright e2e coverage.
- A new feature needs at least matching unit tests — 100% coverage isn't required, but core logic branches must be covered.
